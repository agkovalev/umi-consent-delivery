# Инструкция оператору сервера доставки

## 1. Разделение ролей

Оператор хранит релизы, регистрирует установки и выдаёт разрешения.
Интегратор хранит ключ установки в приватном конфиге сайта, запускает установку
и отдельно активирует релиз. Посетитель получает локальные JS/CSS без обращения
к серверу доставки. Кабинета и веб-администрирования в текущей версии нет.

| Объект | Где хранить | Кому передавать |
| --- | --- | --- |
| Закрытый RSA signing key | В защищённом хранилище оператора, вне работающего сервиса | Не передавать сайтам |
| Публичный signing PEM | У оператора и в доверенной конфигурации клиента | Интегратору отдельно от API |
| Ключ установки | В конфиге конкретного сайта; БД сервиса хранит его хеш | Только интегратору этого сайта |
| Реестр SQLite и релизы | DELIVERY_DATA | Только эксплуатационным процессам |

Домен в реестре — метаданные. Аутентификация идёт по ключу установки, а не по Origin,
Referer или фактическому домену запроса. Скопированный ключ может использоваться с
другой машины до отзыва. Уже скачанные публичные файлы ограничить ключом невозможно.

## 2. Рабочее место и запуск

Команды этого руководства выполняйте в **репозитории umi-consent-delivery** на
машине оператора с доступом к каталогу данных. Сам клиентский ZIP не содержит сервер.
Нужны Node.js 22.22.2+ и закреплённый проектом pnpm; для Docker-пилота — Docker Compose.

```sh
pnpm install --frozen-lockfile
pnpm build
export DELIVERY_DATA="$PWD/.local/service"
```

Для собственного сервера замените DELIVERY_DATA на его постоянный абсолютный путь.
Всегда проверяйте этот путь: CLI иначе использует `.local/service` относительно
текущей папки и может создать отдельный пустой реестр. В новом терминале переменную
нужно установить заново.

Выберите команду `admin` для вашего способа запуска. Для сервера без Docker,
в той же ОС и с тем же DELIVERY_DATA, где работает Node.js:

```sh
admin() { node build/src/cli.js "$@"; }
```

Для работающего Docker-пилота вместо этого определите:

```sh
admin() { docker compose exec -T delivery node build/src/cli.js "$@"; }
```

Далее все команды `admin` используют выбранный вариант. Функцию нужно определять
в каждом новом терминале. Для проверки выбранного реестра:

```sh
admin sites
```

Команда выводит site id, домен, active и target, без ключей. Пустой список может
означать как новый реестр, так и ошибочный DELIVERY_DATA.

### Существующий локальный пилот

```sh
docker compose up -d --build --wait
docker compose ps
```

Compose монтирует `.local/service` хоста в `/data` сервиса. Для операций с живым реестром
используйте `admin` внутри контейнера. Не открывайте живую WAL-базу одновременно
из macOS и Docker Desktop: изменения между этими средами могут быть не видны.
Подписание/импорт с хоста выполняются при остановленном API; закрытого ключа
в контейнере нет. `pilot:prepare` предназначен для учебной подготовки,
не используйте его вместо регистрации настоящего клиента.

### Запуск сервера без Docker

После сборки, в отдельном терминале с тем же DELIVERY_DATA:

```sh
HOST=127.0.0.1 PORT=3100 node build/src/server.js
```

Ожидается запуск HTTP API на loopback:3100. Проверка:

```sh
curl --fail http://127.0.0.1:3100/health
```

Ожидается `{"ok":true}`. Это foreground-процесс: для постоянной работы на сервере
нужно настроить его штатный process manager, постоянный HTTPS reverse proxy,
перезапуск, внешний мониторинг и резервные копии. Конкретный production-хостинг
пока не выбран; данная команда сама production-развёртывание не завершает.
HTTP loopback нельзя выдавать внешним клиентам как endpoint.

CloudPub endpoint текущего стенда — тестовый: зависит от локальной машины и туннеля.
При переводе на постоянный адрес обновите baseUrl у клиентов и повторите doctor --online.

## 3. Подготовить ключ подписи и импортировать релиз

Ключ подписи создаётся **один раз для канала**, не для каждого сайта/релиза.
Если действующий ключ уже существует, используйте его; создание другого ключа
потребует отдельной доставки нового доверенного PEM всем клиентам.

Пример для нового канала; `/secure/consent` замените своим защищённым каталогом:

```sh
mkdir -p /secure/consent
chmod 700 /secure/consent
pnpm admin keygen /secure/consent/private.pem /secure/consent/public.pem
```

Существующие файлы команда не перезаписывает. Сделайте отдельную защищённую копию
закрытого ключа. Не помещайте его в Git, Docker image, web root или клиентский ZIP.

Получите ZIP релиза umi-cookie-consent и sidecar из проверенного релиза библиотеки.
Для Docker-пилота сначала выполните `docker compose stop delivery`: это остановит
только API обновлений, установленные JS/CSS сайтов продолжат работать.
Пример импорта с хоста в выбранный DELIVERY_DATA:

```sh
pnpm admin import 0.6.0 /releases/umi-cookie-consent-v0.6.0.zip /releases/umi-cookie-consent-v0.6.0.zip.sha256 /secure/consent/private.pem
```

После завершения команды на Docker-пилоте выполните `docker compose start delivery`
и проверьте health, в том числе если импорт завершился ошибкой.
Для bare Node в той же ОС импорт может выполняться при работающем API.

Ожидается exit code 0 без ошибки. Проверяются архив, checksums и версия файлов;
создаётся подписанный манифест. Повторный импорт той же версии отклоняется:
релиз неизменяем. Не исправляйте его файлы вручную — подготовьте новый релиз.

Текущий import одновременно подписывает и записывает релиз, поэтому машине запуска
нужны доступ к DELIVERY_DATA и ключу. Ключ не нужен постоянно работающему HTTP API.
Отдельного переноса заранее подписанного релиза с полностью изолированной машины
в этой версии нет. Не копируйте живую SQLite-базу туда-обратно для обхода этого ограничения.

## 4. Выдать доступ новому сайту

Выберите стабильный site id: строчные латинские буквы, цифры, дефис, до 64 символов.
Домен задавайте без протокола и пути, например `example.ru`.
У каждой установки должен быть собственный ключ; не делитесь одним ключом между клиентами.

```sh
admin site-add example example.ru
```

Команда **один раз выводит новый ключ**. Сразу сохраните его в защищённом хранилище.
Не запускайте выдачу в CI, записываемой демонстрации экрана или терминале с общим логом.
Повторный site-add с тем же id не выдаст прежний ключ. Из хеша в БД восстановить его нельзя.

Если удобнее получить ключ в новый приватный файл без вывода на экран, используйте
определённую выше функцию admin (она вызывает Node CLI без вывода pnpm):

```sh
umask 077
set -C
admin site-add example example.ru > /secure/consent/example.token
set +C
```

Это **альтернатива** предыдущему site-add, не вторая регистрация. Файл назначения
должен отсутствовать; проверьте код завершения. `set -C` запрещает перезапись.
Не включайте shell tracing (`set -x`). Передавайте токен защищённым каналом.

Теперь назначьте импортированную версию:

```sh
admin approve example 0.6.0
admin sites
```

Ожидается запись `example`, `active: 1`, `target: "0.6.0"`. Без approve клиент
получит 403. Передайте интегратору универсальный ZIP+sidecar, endpoint, token,
доверенный public.pem, site id и номер версии. Сам ZIP не персонализируется.

Интегратор выполняет doctor --online, install и activate по [инструкции](INTEGRATOR.md).
Попросите подтвердить активную версию и успешную загрузку JS/CSS с сайта, без передачи конфига.

## 5. Выпустить обновление

1. Подготовьте новый релиз в репозитории библиотеки и получите его ZIP+sidecar.
2. Импортируйте новую версию существующим signing key.
3. Разрешите её сначала тестовой установке: `admin approve SITE_ID VERSION`.
4. Интегратор устанавливает, активирует и проверяет сайт.
5. Выдавайте разрешение остальным установкам адресно той же командой.

Назначение новой версии сохраняет прежние grants, чтобы начатые загрузки могли
завершиться. Оно не запускает install/activate на сайтах. Смена target на старую
версию не отменяет защиту клиента от downgrade: для отката используется ранее
установленная локальная версия. Команды отзыва одного отдельного grant пока нет.

## 6. Отозвать или заменить ключ

Блокировка будущих запросов установки:

```sh
admin site-revoke example
admin sites
```

Ожидается `active: 0`; клиент получает 401. Сайт продолжает использовать уже
установленные JS/CSS. Удаление файлов с клиентского сайта не выполняется.

Замена потерянного/скомпрометированного ключа:

```sh
admin site-rotate example
```

Команда выдаёт новый ключ один раз, немедленно отменяет старый и **снова включает
установку**. Назначение версии и grants сохраняются. Передайте новый токен
интегратору, он меняет config.json и запускает doctor --online. До замены конфигурации
его запросы не пройдут, но установленный баннер работает. Для сохранения блокировки
после выдачи нового ключа повторите site-revoke до передачи доступа.
Signing key/public.pem при такой ротации не меняются.

## 7. Повседневное администрирование

```sh
admin sites
docker compose ps
docker compose logs --tail 100 delivery
```

Docker-команды относятся только к нашему Docker-пилоту. При запуске без Docker
смотрите статус и журнал выбранного process manager. Не прикладывайте конфиги/токены
к обращениям; HTTP-журнал сервиса исключает Authorization и query string.

Административные действия сохраняются в таблице SQLite `audit`; отдельной команды
просмотра журнала/редактирования доменов/удаления установки сейчас нет. Не правьте
реестр вручную для обхода авторизации или ограничений релизов.

| Ошибка клиента | Проверка оператора |
| --- | --- |
| 401 | Правильный реестр, id, active; был ли отзыв или ротация |
| 403 | Импортирован ли релиз, есть ли target и разрешение для этого сайта |
| 429 | Нет ли частого cron/цикла; повтор после Retry-After |
| 503 / integrity | Состояние файлов релиза; не подменять bytes, проверить доверенную копию |
| Сеть/TLS | Процесс сервиса, proxy/туннель, DNS, сертификат и срок его действия |
| Signature failure | Совпадают ли trusted PEM и signing key; остановить выдачу при подозрении на подмену |

## 8. Копии, восстановление и ограничения

Создавайте копию после значимых административных изменений и перед обслуживанием.
Сначала `pnpm build`. Для Docker Desktop остановите API (`docker compose stop delivery`)
перед следующими host-командами и запустите его (`docker compose start delivery`)
после их завершения. Онлайн-копирование без остановки выполняйте только внутри
той же ОС, что и сервис; простой сценарий ниже для Docker использует остановку.
Пример с отдельными новыми каталогами:

```sh
pnpm ops backup "$DELIVERY_DATA" /backups/consent/snapshot-001 /secure/consent/public.pem
pnpm ops verify /backups/consent/snapshot-001 /secure/consent/public.pem
pnpm ops restore /backups/consent/snapshot-001 /backups/consent/restore-test-001 /secure/consent/public.pem
```

Родители каталогов должны существовать; назначение должно отсутствовать и быть вне
источника. Команды выводят только количества релизов и сайтов. Restore не переключает
работающий сервис и не перезаписывает существующую БД.

Реестр восстановится на дату снимка. До открытия API повторите более поздние отзывы,
ротации и изменения разрешений. Копии хранятся отдельно от signing key и отдельно
от рабочей машины; автоматического расписания, шифрования и внешнего хранилища
в текущем комплекте нет. Полная процедура — [Эксплуатация](OPERATIONS.md).

Лимиты пилота: 600 запросов/мин на процесс, 60/мин на site id; health исключён.
Они не заменяют защиту сети/reverse proxy. Масштабирование на несколько процессов,
платежи, кабинет и автоматическая смена trust root в текущий комплект не входят.

## 9. Собрать установочный ZIP

На машине разработчика/оператора из репозитория:

```sh
pnpm check
pnpm client:archive
```

Получатся `release/umi-consent-delivery-client-v0.1.0.zip` и `.zip.sha256`.
Версия берётся из package.json; это версия клиента доставки, не библиотеки.
Архив собирается по allowlist, без `.local`, действующих конфигов, PEM и ключей.
Передавайте оба файла; секрет и доверенный PEM — отдельно. Подготовка архива не
создаёт Git-тег, не публикует релиз и не выдаёт ключ ни одному сайту.
