# Архитектура и протокол v1

## Доступ

Оператор регистрирует site id и домен, выдаёт случайный 256-битный ключ и разрешает версии. База хранит SHA-256 ключа. Ключ возвращается CLI один раз; `site-rotate` заменяет его и включает установку, `site-revoke` блокирует все запросы. Одобрение новой версии сохраняет ранее выданные разрешения для загрузок, начатых до переключения.

Домен — метаданные реестра, аутентификация выполняется ключом. Украденный ключ можно использовать с другого сервера. Отзыв останавливает будущие выдачи; уже установленные публичные JS/CSS продолжают работать. Журнал SQLite `audit` фиксирует административные действия без ключей. HTTP-журнал не содержит Authorization или query string.

## Релизы и подписи

Импорт принимает версию без `v`, ZIP, доверенный SHA-256 sidecar и путь к офлайн RSA-ключу не короче 3072 бит. Проверяет размер архива, имена и размеры ZIP-записей, dist/checksums.sha256 и версии баннеров JS/CSS. Из ZIP извлекаются только четыре фиксированных файла; остальные записи не распаковываются. Совпадение sidecar подтверждает целостность, а доверие к источнику обеспечивает оператор, получивший архив из проверенного релиза.

В подписанный JSON входят schema=1, version, archiveSha256 и files: name, size, sha256. Подпись RSA PKCS#1 v1.5/SHA-256 вычисляется по точным UTF-8 байтам JSON. Envelope содержит manifest и signature в base64, keyId = SHA-256 точных байтов SPKI PEM публичного ключа. Нельзя менять переводы строк в PEM после выдачи клиенту. Сервер хранит envelope, но не закрытый ключ. Версия не перезаписывается.

Проверка клиента: закреплённый PEM → подпись → схема/имена/размеры → SHA-256 файлов → публикация полного каталога → отдельная активация. `openssl_verify` считается успешным только при `=== 1`.

Подпись не доказывает наличие самого свежего релиза и не защищает от удержания обновлений. Клиент помнит наибольшую увиденную подписанную версию и отказывает серверному downgrade. Откат разрешён на проверенную локальную копию. Для смены/компрометации signing key нужно вручную доставить новый доверенный PEM клиентам; автоматическая ротация trust root не входит в пилот.

## HTTP API

Все `/v1/*` запросы требуют `Authorization: Bearer <token>`. Нет CORS и браузерных cookies.

| Запрос | Ответ |
| --- | --- |
| GET /health | 200, `{ "ok": true }` |
| GET /v1/manifest | 200, подписанный envelope текущей одобренной версии |
| GET /v1/releases/{version}/files/{name} | 200, точные байты одного из четырёх разрешённых файлов |

401 — отсутствующий, неверный или отозванный ключ; 403 — версия/файл не разрешены или версия не назначена; 429 — превышен общий лимит или лимит установки, с Retry-After; 503 — хранилище содержит повреждённый файл. Ответы private/no-store. Клиент не следует redirect и не передаёт ключ другому origin. Лимиты и резервные копии описаны в [эксплуатации](OPERATIONS.md).

Файлы: umi-cookie-consent.min.js, umi-cookie-consent.min.css, THIRD_PARTY_NOTICES, DOMPURIFY-LICENSE.txt. Браузер не обращается к delivery API. Внешний транспорт требует HTTPS; исключение клиента — HTTP на localhost/127.0.0.1 для пилота.

## Хранилище

SQLite: sites, grants, releases, audit; schema version 1, foreign keys и WAL. API читает реестр на каждый запрос. Данные релизов находятся в `DELIVERY_DATA/releases/{version}`. Обновления схемы должны сохранять права и неизменяемость релизов. В пилоте SQLite доступна только локальным процессам; веб-администрирования нет.

Основания: [TUF: целостность и подписи](https://theupdateframework.io/docs/overview/), [PHP OpenSSL verification](https://www.php.net/manual/en/function.openssl-verify.php), [OWASP: защита секретов](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html).
