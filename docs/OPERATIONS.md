# Эксплуатация пилота

## Резервная копия и проверка восстановления

После `pnpm build` команды выполняются на хосте из корня репозитория:

```sh
pnpm ops backup .local/service .local/backup-2026-09-29-ops .local/pilot/private/public.pem
pnpm ops verify .local/backup-2026-09-29-ops .local/pilot/private/public.pem
pnpm ops restore .local/backup-2026-09-29-ops .local/restore-drill-2026-09-29 .local/pilot/private/public.pem
```

Эти имена уже использованы при проверке 2026-09-29. Для следующего запуска задайте
новые имена каталогов. Родительский каталог должен существовать. Команды отказывают
при существующем назначении, включая пустой каталог, и не перезаписывают рабочую базу.
Назначение не может находиться внутри источника. Результат содержит только количество
релизов и установок, без ключей.

`backup` использует SQLite Online Backup API для согласованного снимка WAL-базы,
после чего копирует только четыре файла каждого зарегистрированного в снимке релиза.
Релизы неизменяемы, а импорт публикует файлы до записи в БД. Незавершённые импорты,
архивы, посторонние файлы и приватный signing key в копию не включаются.
Во время копирования нельзя вручную удалять/менять опубликованные релизы.
Основание: [SQLite Online Backup API](https://www.sqlite.org/backup.html).

Проверяются SQLite integrity_check, foreign_key_check, schema version 1, подписи
манифестов по отдельно переданному доверенному PEM, фиксированные имена, размеры
и SHA-256 файлов. Символические ссылки вместо файлов/каталогов релизов отклоняются.
Лимиты: база до 256 MiB, envelope до 128 KiB, каждый asset до 5 MiB.
Каталог создаётся с правами 0700, файлы — 0600; запускать сервис после восстановления
нужно от пользователя с доступом к этим файлам.

`snapshot.json` записывается последним и содержит SHA-256 БД. Отсутствующий или
неверный marker означает незавершённую/повреждённую копию. При штатной ошибке
созданный командой каталог удаляется; после аварийного завершения может остаться
неполная копия, которую `verify` не примет. Снимок остаётся неизменным после создания.

Копии содержат реестр клиентов, хеши ключей и журнал. Храните их в доверенном
хранилище с ограниченным доступом: checksum БД обнаруживает повреждение, но не
аутентифицирует административные записи против злонамеренной подмены всей копии.
Встроенного шифрования, автоматического расписания и внешнего хранилища пока нет.
Локальная копия на том же диске не защищает от потери машины.
Offline signing key и доверенный public.pem резервируются отдельно оператором.

## Переключение после аварии

1. Проверьте доверенную копию и восстановите в новый каталог.
2. Сверьте административные изменения после даты снимка: **восстановление возвращает
   права, ключи и отзывы на дату копии**. Повторите более поздние отзывы/ротации
   до открытия API. Подписи релизов не защищают от восстановления старого реестра.
3. Остановите сервис, назначьте восстановленный каталог как DELIVERY_DATA/mount,
   проверьте права пользователя процесса и запустите сервис. Для Compose текущий
   mount задан в compose.yaml; автоматического переключения этой командой нет.
4. Проверьте health, доступ разрешённой установки и отказ отозванному ключу.
   Исходный каталог сохраните до завершения проверки.

Каталог для учебного восстановления не обслуживается работающим сервисом.
После начала работы БД изменяется; `snapshot.json` больше не описывает live-базу.
Новые копии делаются командой `backup`, а не копированием sqlite/WAL вручную.

## Лимиты

- 600 запросов за фиксированное окно 60 секунд на один процесс, до аутентификации.
- 60 запросов за то же окно на site id после аутентификации, совместно для манифеста
  и файлов. Ротация токена и подмена X-Forwarded-For не обходят лимит site id.
- Ответ 429 содержит Retry-After (секунды) и private/no-store. PHP-клиент завершает
  попытку без смены активной версии; повторите команду позже, автоматического retry нет.
- GET /health исключён из счётчиков для Docker healthcheck.
- Лимиты находятся в src/limits.ts, действуют в памяти одного процесса и сбрасываются
  при перезапуске. На границе окон возможны два последовательных burst. Это ограничение
  работы приложения, не защита от сетевого DDoS. Общий лимит может временно затронуть
  все установки; для production нужен внешний proxy с собственными лимитами.
- Forwarded-заголовки не используются для доверия или идентификации установки.

Compose ограничивает delivery: 256 MiB RAM, 1 CPU, 128 PID; json-file журнал
ротируется по 10 MiB, максимум 3 файла. Включён restart: unless-stopped.
Это начальные значения для пилота, нагрузочная ёмкость не измерялась.

## Что проверено

2026-09-29: реальная работающая WAL-база скопирована и восстановлена отдельно:
2 релиза и 2 установки, все подписи/файлы прошли проверку. Тесты проверяют сохранение
grants, ротации/отзыва, журнала и точных bytes после восстановления; отказы при
повреждениях, неверной подписи, symlink, отсутствующем файле и попытке перезаписи.
HTTP-тесты проверяют общий/site лимиты, Retry-After, сброс окна и spoofed forwarding.
PHP-тесты подтверждают сохранение активной версии при 429 на манифесте и asset.

Production-hosting, внешнее хранение копий, расписание и мониторинг ещё не настроены.
